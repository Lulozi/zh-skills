# 中文工程规范 · 项目体检（health-check-zh）

当用户要求体检、健康检查、评估一个项目的中文规范性时激活本技能。产出**评分 + 修复清单**，让一个项目的"中文工程健康度"可量化、可追踪。

## 检查维度（共 100 分）

### A. 文档健康（25 分）
- [ ] 有 README，且**开头一句话定位清楚**（是什么、解决什么）。（10）
- [ ] README 有快速开始，能照着跑起来。（5）
- [ ] 无翻译腔句式（搜"进行一个""通过使用""需要注意的是"等）。（5）
- [ ] 有 LICENSE、CHANGELOG（或 commit 规范）。（5）

### B. AI 协作健康（15 分）
- [ ] 有 `CLAUDE.md`（或 `AGENTS.md`），AI 能读懂项目。（5）
- [ ] `.claude/skills/` 或 `.cursor/rules` 中有项目自己的技能/规则。（5）
- [ ] CLAUDE.md 里写清了命令（build/test）和约定，而非空话。（5）

### C. 命名健康（20 分）
- [ ] 无拼音命名残留（`jine`、`leixing`、`dataList` 混拼音）。（10）
- [ ] 命名风格统一，无神秘缩写。（10）

### D. 代码卫生（20 分）
- [ ] 无大量 `console.log` / `TODO` / `FIXME` 残留（>5 处扣分）。（10）
- [ ] 注释与代码一致，无整段被注释的死代码。（10）  
  
### E. 注释卫生（20 分）
- [ ] 注释无排版符号污染：不含 `===`、`---`、`···` 等重复符号分隔线（含 `··· 标题 ···` 式装饰包裹），尤其不出现在文件头。（10）
- [ ] 注释无翻译腔（`// 对数据进行一个排序的操作`）、无废话注释（`// 遍历数组`）、无过时注释。（5）
- [ ] 注释只描述模块 / 文件 / 代码块的功能、意图与实现方式，不写版本变更史（如 `// v1.2：修复了 X`、`// 2.0 起改为 Y` 等带版本号的记录）；变更历史应写在提交日志或 CHANGELOG，而非注释。（5）

## 评分档位

| 分数 | 评价 |
|------|------|
| 90–100 | 🟢 优秀，可以直接当团队样板 |
| 70–89  | 🟡 良好，有零星问题，修一下更好 |
| 50–69  | 🟠 一般，中文规范基本没落地 |
| 0–49   | 🔴 危险，AI 都看不懂，建议先补文档 |
| <0     | ⚫ 非常危险，规范严重缺失且问题大量堆积，优先治理 |

> 额外扣分：任一得分点不符合项 **> 5** 时，超出部分每项再扣 1 分；**每个得分点独立封顶 -10**（而非全局只 -10），各点累加，因此总分允许为负（低于 0 即"非常危险"）。例如注释卫生里"排版分隔线 50 处"与"变更史 90 处"两个得分点可各扣满 -10，合计额外 -20。

## 输出格式

```
## 🏥 zh-skills 健康体检报告

项目：xxx
总分：72/100 🟡 良好

### ✅ 做得好的
- README 开头有一句话定位

### ⚠️ 待修复（按收益排序）
1. [命名] src/utils/date.ts:12 `shijian` → `createdAt`（拼音命名，收益高）
2. [文档] README 缺快速开始
3. [AI] 无 CLAUDE.md，AI 协作体验为零

### 一键修复建议
运行 `zh-skills init` 安装中文工程规范 skills，再按上述清单逐项修。
```

## 体检操作指引

1. 用 `Glob`/`Read` 看项目根目录、README、`src/` 抽样文件。
2. 用 `Grep` 搜拼音模式、翻译腔模式、`console.log`/`TODO` 计数、注释中的 `===`/`---`/`···` 等排版符号分隔线，以及注释里"修复/修改"等变更操作记录与 `v1.2：` 这类版本号变更史（应进提交日志 / CHANGELOG）。
3. 逐项打分，先给总分，再给"做得好"和"待修复"。
4. 每个待修复项：**位置 + 问题 + 改成什么**，一句话能执行。
5. 修复建议按"收益/成本"排序，先推性价比最高的（通常是无拼音命名 + 补 CLAUDE.md）。
